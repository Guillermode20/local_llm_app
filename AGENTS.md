# Repository Guidelines

## Project Overview

This is a **local-first LLM chat application** built with Flutter (Dart). It lets users import GGUF model files and run inference entirely on-device via FFI bindings to llama.cpp (or a compatible C inference wrapper). No cloud APIs, no model bundling — users bring their own models.

### What this app does (end-to-end)

1. **Import models** — User picks a `.gguf` file via file picker, the app copies it to app-private storage, validates the GGUF header, computes a SHA-256 hash, writes a sidecar JSON with metadata, and registers it in the local SQLite database.
2. **Manage models** — List imported models, view metadata (architecture, quantization, parameter count), set one as "active", delete models (removes the GGUF file + sidecar + DB row).
3. **Chat** — Create conversations, send user messages, stream assistant replies token-by-token from the local inference engine, display markdown-rendered responses, edit/resend/regenerate messages with branching.
4. **Inference** — Spawns a dedicated Dart isolate that owns all C FFI state. Commands are sent via `SendPort`, tokens stream back via events. Model loading, generation, cancellation, and unload all happen on this isolate.

```
    │
    ▼
GenerationDoneEvent → finalise metrics, close stream
```

## Key Architectural Patterns

### 1. Inference Isolate Pattern

The inference engine runs on a **dedicated Dart isolate** to prevent UI jank and contain crashes. This is the most architecturally significant pattern in the app.

**Contract:**
- Main isolate ↔ Isolate communication via 2 `SendPort`/`ReceivePort` pairs (commands + events).
- Commands are typed sealed classes (`InferenceCommand` hierarchy).
- Events are typed sealed classes (`InferenceEvent` hierarchy).
- The isolate owns global mutable state (`_gCtx`, `_gBindings`, etc.) — the main isolate never touches native pointers.
- On isolate death (crash), the main isolate resets all state and surfaces an error to the user.

**Lifecycle:**
1. `InferenceService.start()` → `spawnInferenceIsolate()` → isolate entry point starts listening on command port.
2. `loadModel()` → sends `LoadModelCommand` → waits for `ModelLoadedEvent` or `ModelLoadFailedEvent`.
3. `generate()` → sends `GenerateCommand` → returns broadcast `Stream<TokenEvent>`.
4. `cancel()` → sends `CancelCommand` → native atomic flag stops generation → polling timer detects and sends `GenerationCancelledEvent`.
5. `unloadModel()` → sends `UnloadModelCommand` → frees C context → awaits completion event.
6. `dispose()` → sends `ShutdownCommand` → isolate exits.

**Async native execution:** Generation runs on a native thread (not the Dart event loop). A periodic 50ms timer polls `llm_get_generation_status()` to detect completion. This design allows the isolate's event loop to remain responsive to cancel commands and other messages during generation.

### 2. Riverpod Provider Structure

The app uses **Riverpod with code generation** (`@riverpod` annotations) for state management.

**Provider categories:**
- **Singletons** (`Provider`) — database, model repository, chat repository, inference service. Initialised in `main()` and injected via `ProviderScope(overrides: [...])`.
- **Notifier providers** (`NotifierProvider`) — `ModelListNotifier` (model list), `ActiveModelNotifier` (active model), `ChatControllerNotifier` (per-conversation chat lifecycle). Family variant for per-conversation state.
- **Stream providers** (`StreamProvider`) — `conversationListProvider` (watches DB for conversation list), `conversationMessagesProvider.family` (watches messages per conversation).
- **State providers** (`StateProvider`) — `activeConversationIdProvider`, `modelImportStateProvider`.

**Important:** Providers that depend on initialised singletons use `overrideWithValue` at the app root, not default constructors.

### 3. Database & Sidecar Dual Storage

Model metadata is stored in **two places** for different lifetimes:

| Storage | Purpose | Schema |
|---------|---------|--------|
| **Sidecar JSON** (`{uuid}.json`) | Source of truth. Survives DB reset. | `{id, original_name, size_bytes, sha256, imported_at, metadata:{...}, profile:{...}}` |
| **Drift SQLite** (`local_llm_app.db`) | Fast queries, reactive streams, joins. | `model_entries`, `conversations`, `messages`, `benchmarks` tables |

On app startup, `ModelRepository.refresh()` scans sidecar files and syncs Drift to match. If a sidecar file is deleted manually, the Drift row is removed. If a new sidecar appears (e.g., from backup restore), a Drift row is created.

**Conversations and messages** are stored **only** in Drift (no sidecar). They use auto-increment integer IDs. Messages have `parentMessageId` for threading and `archived` flag for edit-and-resend branching.

### 4. Model Import Pipeline

```
File picker → size check (< 50GB, > 100 bytes)
  → Read first 100KB → GGUF header parse (validate it's really a GGUF)
  → Copy entire file to app-private storage (4MB chunks)
  → Compute SHA-256 during copy
  → Write sidecar JSON with metadata
  → Return ModelImportResult
```

The import is exposed as a `Stream<ModelImportState>` so the UI can show progress (bytes copied / total bytes, phase label).

### 5. Edit-and-Resend Branching

When a user edits a message and resends:
1. `ChatRepository.archiveBranchFrom(messageId)` — marks that message and all descendants as `archived`.
2. `ChatControllerNotifier.sendMessage()` — creates a new user message (with the edited content) and a new assistant message placeholder.
3. Old messages stay in the DB (archived) — they can be revisited but are excluded from the active query.

This avoids data loss while keeping the active conversation clean. The branch point is tracked via `parentMessageId`.

### 6. Chat Template Handling

The app currently hardcodes a **Gemma 3n chat template** as the Dart-side fallback (`formatGemma3nChat()` in `chat_template.dart`). The C wrapper's `llm_apply_chat_template` function is available and queried at model load time, but the Dart-side fallback is used for generation.

**To add support for a new architecture**, you'd need to:
1. Add a new Dart-side template function (like `formatGemma3nChat`).
2. Detect the architecture from `ModelMetadata.architecture` and dispatch to the correct template.
3. Update or rely on the C wrapper's `llm_apply_chat_template` for models that embed their own template.

## FFI & Native Code

### Native Library Interface

The C wrapper exposes a stable ABI defined in `inference_bindings.dart` (auto-generated by `package:ffigen`). The library name varies by platform:

| Platform | Library |
|----------|---------|
| Android | `libinference.so` |
| Linux | `libinference.so` |
| Windows | `inference.dll` |
| macOS/iOS | `DynamicLibrary.process()` (statically linked) |

### The token callback

The C generation functions accept a callback of type `llm_token_cb` which is invoked from the native thread for each token. In the Dart isolate, this callback posts a `TokenEvent` to the event `SendPort`:

```dart
void _onToken(Pointer<Char> token, int len, int isFinal, Pointer<Void> _) {
  final str = (len > 0) ? token.cast<Utf8>().toDartString(length: len) : '';
  _gEventSink?.send(TokenEvent(token: str, isFinal: isFinal != 0));
}
```

The `NativeCallable` wrapping this callback must be kept alive (stored as `_gTokenCallable`) to prevent garbage collection.

### GPU Backend

- `BackendHint` enum maps to integer values passed to `llm_load_model`: auto(0), cpu(1), vulkan(2), opencl(3).
- `BackendProbeResult` captures Vulkan/OpenCL availability via `llm_probe_backends`.
- The host build script (`scripts/build-vulkan-shaders-gen-host.sh`) builds llama.cpp with `-DGGML_VULKAN=ON` for shader compilation.

## Coding Style & Naming Conventions

- **Indentation**: 2 spaces per level (Dart standard).
- **Style**: Follow `package:flutter_lints` rules (enforced via `analysis_options.yaml`). Configured with `custom_lint`, `riverpod_lint`, and `unawaited_futures: error`.
- **Naming**:
  - `lowerCamelCase` for variables, functions, method names, file names.
  - `UpperCamelCase` for classes, enums, type definitions.
  - `lowercase_with_underscores` for file and directory names.
  - `snake_case` for test function names that describe scenarios.
- **Sealed classes for state/events**: Use `sealed class` hierarchies for finite state machines (e.g., `InferenceCommand`, `InferenceEvent`, `ChatControllerState`, `ModelImportState`). This enables exhaustive pattern matching.
- **Riverpod**: Annotate providers with `@riverpod` and use Riverpod code generation. Keep providers in dedicated files suffixed with `_providers.dart` (e.g., `chat_providers.dart`).
- **Avoid `async` in factory constructors**: Use static methods named `create()` or `open()` for async initialisation instead.
- **Drift**: Prefer `watch()` over `get()` for reactive UI-bound queries. Use custom SQL (via `customSelect`) for complex queries (aggregations, subqueries).
- **FFI memory management**: Every `calloc.*` must have a paired `calloc.free` in a `finally` block. Native strings allocated for prompts are freed immediately after the C call copies them.

| `_ensure*` | `_ensureLoaded`, `_ensureNotGenerating` | Precondition guards |

| `Command` suffix | `LoadModelCommand`, `CancelCommand` | Inference isolate commands |
| `State` suffix | `ChatControllerState`, `ModelImportState` | Finite state machine states |

## Testing Guidelines

- **Framework**: `flutter_test` with Dart's built-in test runner.
- **Location**: Place test files in `test/`, mirroring the `lib/src/` structure where possible.
- **Coverage**: No enforced threshold yet. Run `flutter test` to verify.
- **Test naming**: Use descriptive `snake_case` names that explain the scenario and expected outcome.
- **What to test**:
  - Pure-Dart logic extensively: GGUF parser (edge cases, all value types, truncated data, invalid magic), chat template formatting, model profile serialization, metadata display helpers.
  - Repository logic with in-memory databases (Drift's `NativeDatabase.memory()`).
  - Widget tests for key components (message bubble states, composer, model manager list).
  - Integration tests for the import → chat → generation flow (mock the FFI layer).

## Agent-Specific Instructions

### Before editing
1. **Read the full file first** — not snippets. Study surrounding code to match existing conventions and interface contracts.
2. **Check for patterns** — If adding a new command/event type, follow the sealed class pattern in `inference_command.dart`/`inference_event.dart`. If adding a new provider, add it to the appropriate `_providers.dart` file following existing patterns.
3. **Understand the data flow** — Trace through the layers (UI → provider → repository/service → DB/FFI) before modifying any layer.

### After editing
1. Run `make analyze` — fix all lint errors (especially `unawaited_futures`, riverpod lint rules).
2. Run `make test` — ensure existing tests still pass.
3. If you modified annotated source files (Drift, Riverpod annotations, JSON serializable classes), regenerate `.g.dart` files with `dart run build_runner build --delete-conflicting-outputs` and commit the generated files.

### Key invariants to preserve
- **Never import `dart:io` in UI-layer files** (use platform abstractions or keep it in service/repository layers).
- **Never pass FFI pointers** (`Pointer`, `llm_ctx`) across isolate boundaries or into the UI layer — they stay in the inference isolate.
- **Every `calloc` allocation must be freed** in a `finally` block — always.
- **InferenceService must never block the main isolate's event loop.** Generation is async; use streams, not `await` on native work.
- **The sidecar JSON is the source of truth for model metadata**, not the Drift database. The `refresh()` method reconciles Drift to match sidecars.
- **Do not edit files in `third_party/`** — those are git submodules.
- **Generated `.g.dart` files are checked in** — update them with `build_runner`, never manually.

### When adding a new architecture/chat template
1. Add a new Dart-side formatting function in `chat_template.dart` (model after `formatGemma3nChat`).
2. In the inference/chat pipeline (currently `chat_providers.dart`'s `ChatControllerNotifier.sendMessage()`), detect the architecture and dispatch to the correct template.
3. The C wrapper's `llm_apply_chat_template` can also be used for models with embedded templates — wire it as a higher-priority path.

### When adding new screens or widgets
1. Add the screen file to `lib/src/ui/screens/` or widget to `lib/src/ui/widgets/`.
2. Use `ConsumerWidget` or `ConsumerStatefulWidget` from `flutter_riverpod` for state access.
3. Follow the Material 3 theme (use `Theme.of(context).colorScheme.*`, `useMaterial3: true`).
4. Register the route in the appropriate parent screen's navigation calls.

### When working with native builds
- The host build script (`scripts/build-vulkan-shaders-gen-host.sh`) builds llama.cpp with Vulkan support for shader compilation. It's run on the host machine during development.
- Android cross-compilation and the full native build pipeline are not yet wired (`make build-native-android` is a TODO). If wiring them, follow typical llama.cpp Android cross-compilation with CMake toolchain files.
